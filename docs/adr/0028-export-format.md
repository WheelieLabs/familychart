# ADR-0028: Exports are streamed, versioned zips led by a manifest

**Status:** Accepted — Person and Household exports and the restore engine implemented; protected exports build on them

## Context

The only way data left an instance was a per-Person zip of CSVs and a loose `data.json`, assembled in memory. Nothing could read it back, it named entries after stored files, and nothing identified which version of FamilyChart made it. Restore, the Household export and passphrase protection all need one written contract between the exporting and importing sides, and a large household must export on a small server.

## Decision

- **Manifest first.** `manifest.json` is the first zip entry: an integer `format_version` (starting at 1), `scope` (`person` or `household`), the producing `app_version`, `exported_at`, the `sections` present, per-section `counts`, and `skipped_files` (bundle path and reason for each file that could not be included). The manifest is built as a header (`format_version`, `scope`, `app_version`, `exported_at`) and contents (`sections`, `counts`, `skipped_files`) so a protected export can keep only the header plus `protected: true` readable and encrypt the rest.
- **Forwards-only compatibility.** The format version rises whenever a section is added. An importer reads any lower version and refuses a higher one, naming the producing app version. A file with no manifest (made before restore existed) is refused. Encryption is a container property and does not change the version.
- **JSON is the source of truth.** `person.json` carries the Person, their history and the configuration they use. Every cross-reference is a bundle-local id (small integers unique per kind within the file); `db_id` fields are informational and never used to restore. Curated catalogues (observation types, test metrics) travel as name and `is_active` only. The readable copies under `csv/` are by name and never imported.
- **Neutral entry names.** Entries never contain a Person's name or a stored file name: `attachments/photo.<ext>`, `attachments/report-<n>.<ext>`. Stored names live in the structured data (`original_name`).
- **Passphrase protection.** Optional and off by default. A protected export is an AES-256 zip (WinZip AES). `manifest.json` stays first and unencrypted, and then holds only the header plus `protected: true`: no section list, counts, names or dates of birth. A small encrypted `check` entry follows, so a wrong passphrase fails before anything is staged. `contents.json`, encrypted next, holds the section list, counts and skipped files. Every other entry, including the CSV copies, is encrypted. Entry names stay the neutral bundle-local ids above, so a name or a stored file name is never visible. The passphrase is generated by the app (twenty characters from an unambiguous alphabet, shown in four groups of five), shown once, and not stored, logged or written into the audit row. The audit row records that the export was protected. Encryption does not change `format_version`. Stock Windows Explorer and `unzip` cannot open the file; 7-Zip, Keka and WinZip can. There is no way to recover a lost passphrase.
- **Streamed, one attachment at a time.** One builder ([`lib/export/export-zip-stream.ts`](../../lib/export/export-zip-stream.ts)) appends each entry only after the previous one is written and advances only as the reader pulls, so at most one attachment is in memory. Already-compressed files (JPEG, PNG, WebP, PDF and similar) are stored without recompression. File presence is checked before streaming so the manifest can list missing files.
- **Household layout.** Scope `household`: `manifest.json`, then `household.json`, then one `people/<id>/` folder per Person (inactive included). The folder name is that Person's bundle-local id, never their name. Inside the folder is the same payload a standalone Person export produces (`person.json`, the readable CSVs, and `attachments/`), without a second manifest. `household.json` holds the shared parts: the full medication catalogue (groups, membership, frequency rules, active flags), Accounts as credential-free invite descriptors (email, role, reports flag, active flag, original sign-in method, Personal-link as a bundle-local Person id), Favourites (bundle-local Account, Person and medication ids), instance settings from the registry that are neither secret nor platform-locked, curated catalogue name-and-flag lists, and durable per-user preferences. Those preferences are a `user_settings` section keyed by the bundle-local Account id and Person id already used for Accounts and Persons: `locale.timezone`, hydration pacing (`active_start`, `active_end`, `glass_size`), and the five notification booleans (PRN, prescribed, overdue, observations, hydration). A Person export carries only that Person's own settings, the ones held by their Personal-link Account, including the notification preferences that Account holds for the Person themself, keyed by the bundle-local Person id. The section never contains an email or an Account uid. Passwords, MFA secrets, sessions, invite tokens, App lock, push subscriptions, the audit log, transient hydration keys (`muted_until`, `last_nudge_at`, `last_record_at`) and client-side preferences are never carried. Adding the section raised the format version by one. An older importer refuses that version. A newer importer reads a lower version that lacks the section and applies nothing.
- **Slot outcomes.** Each Person payload carries a `slot_outcomes` section: what happened to each Scheduled slot (`assignment_id`, `local_ymd`, `slot_hhmm`, `result`, `offset_minutes`, `missed_cause`, `administration_id`). `assignment_id` and `administration_id` are the bundle-local ids of the assignment and attached dose (null for a Missed slot), so a household export needs no extra section and restore maps each row onto the restored assignment and dose. Slot outcomes joined format version 2 with the per-user settings, because 1.1.0 is not public and no released importer has seen either section; the version did not rise a second time. An importer reading an export without the section applies nothing for it. Restore counts a slot already on the instance (same assignment, day and slot) as a duplicate and never overwrites it, skips a row whose assignment or dose was not restored, and refuses an export whose slot outcome has an unknown result or an inconsistent dose link.
- **Authorisation and accountability.** An Admin may export any Person, inactive included; any other Account only its own Personal-linked Person, whatever its Household Role. The household export is Admin-only. Every export writes one `EXPORT` audit row (scope, Person or Person count, counts, format version, no health values), and a per-Person in-flight count ([`lib/export/export-registry.ts`](../../lib/export/export-registry.ts)) is held for the life of the stream so erase can refuse while a download is running. A household export counts every Person it includes.

## Consequences

- The previous `data/*.csv` + `data.json` layout is gone; nothing ever imported it.
- An export that cannot read a file still completes, and says so in `skipped_files`; a file that disappears between the presence check and its read aborts the download rather than writing a manifest that lies.
- The in-flight count is process-local, which matches the single-process deployment.
- The restore engine reads this format. It refuses a zip with no `manifest.json`, and a `format_version` higher than it understands, naming the producing app version. A staged upload is planned without writing, then applied in one database transaction; files follow the commit.
- No new environment variable for export. Restore upload size is `FC_RESTORE_MAX_UPLOAD_MB` (see the environment inventory).
